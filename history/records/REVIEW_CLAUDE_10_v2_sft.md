# Claude 审核 10｜G1 定案；GRPO 0/20 的原因和 v2 SFT 补齐

日期：2026-10-24。依据：CLAUDE09_RESULTS.md 和 Codex 的口头回报。

## 1. G1 定案：盆地分叉是弛豫路径造成的，评分器维持放行
- 用正式协议从理想格点出发，MACE 仍然回到原来的末态。把 DFT 末态放进 MACE 再弛豫 26 步，占位不变，而且比 MACE 原末态低 0.354 eV。DFT 那边，DFT 末态也比 MACE 末态低 0.805 eV。**两种方法对"哪个盆地更低"的判断一致**，分叉来自弛豫路径，不是势能面上的矛盾。
- 这个例子正好说明，从理想格点直接弛豫会卡在局部盆地里，**需要搜索**。可以写进论文的动机部分。
- 需要如实报告的两点：MACE 低估了两个盆地的能差（0.35 对 0.81 eV），偏差大于 0.2 eV 的整体 RMSE，但这只有一个例子。另外，在更严的收敛判据下末态是否仍是极小点，可以在 CPU 上免费补测一次，优先级低。

## 2. GRPO 650 合法率 0/20：闸门起了作用，但这个结果是可以预见的
- 650 用的是 633 的适配器，而 633 只用旧格式练了 64 条短样本，**从来没有见过 v2 局部动作格式**。模型把状态列表当成动作输出，是意料之中的事。这不是 GRPO 的问题，原因是缺了一步 v2 SFT。这一项算我审核时漏看了：放行 GRPO 冒烟之前，本该要求先做 v2 SFT。
- **补齐路线**（全部在冒烟池内，需要用户确认用途，见第 4 节）：
  1. **v2 D0 小规模采集**：SA、GA、随机搜索的教师轨迹，先采 16–64 条，每条 8 步，用正式 BFGS/0.03/300 协议。这一步顺带测出正式弛豫的 A100 耗时。
  2. **格式增强数据**：从状态直接枚举合法动作，生成几千条"状态 → 合法动作"样本，不调用 MACE，只用来教格式。所有臂共用同一个 SFT 初始化，所以不影响公平性，在计划里注明即可。
  3. **v2 SFT**，然后用 80 个留出状态做离线合法率测试（≥76/80，不调用 MACE）。
  4. 合法率通过后，**再跑一次 GRPO 冒烟**（≤2 卡时，19/20 闸门不变）。
  - 备选：如果 SFT 后合法率仍不达标，就改用约束解码（按状态生成 logits 掩码）。掩码后的分布要同时用于采样概率和 PG 概率，保持一致。这个方案要先报给我，不能直接换上。
- prompt 和 schema 先在 CPU 上离线诊断（不加载 GPU 模型的部分），可以直接做。

## 3. 定标：物理成本不是瓶颈，组内要批量弛豫
- 648 的实测：batch16 单点约 53 个结构/秒；FIRE 40 步，16 个副本一共 12.6 s，单例 1.24 s，相当于每次 E/F 约 20–30 ms。粗算一次正式 BFGS 弛豫（约 87 步）单例约 3 s，528 次约 26 分钟，用组内批量还会更短。所以 **16 组每轮放进 1.5 h 应该可行**，真正的大头是 LLM 生成和 PG。这一点要以第 2 节第 1 步的实测为准。
- **实现建议**：同一组里 G=4 条回合同步推进，每一步把 4 个弛豫打成一个 batch（batch4 的等价性已经验证过），并把这一项计入计划。
