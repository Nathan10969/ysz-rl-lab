## 2. 方案：在现有动作协议上做合法动作 token trie 约束解码（审核 10 预登记的备选）
- **唯一合法集**：用 `env.enumerate_legal_actions(occupancy)`，文本固定为 `Action.to_json()` 的规范形式，站点按升序排列，所以同一个动作不会有正反两种写法。trie 用官方 tokenizer 把每个动作的完整 token 序列（含 EOS）切出来建，不手工拼数字。
- **一套掩码贯穿三条路径**：generate、参考模型打分、更新时的 log-prob，都在同一个前缀掩码下、只在允许的 token 上做 softmax。rollout 要保存 occupancy（或可验证的哈希）以及 trie、tokenizer、namespace 的版本，保证更新时重建的就是采样时的掩码。
- **命名要准确**：这是"逐 token 前缀约束策略"，不等于对原模型在全部合法字符串上做一次全局条件化。合法率是解码器保证的，不代表模型学会了空间关系。论文里的表述是"LLM 作为合法动作集上的策略"。搜索基线本来也只在合法动作里选，所以比较是公平的。
- **损失的平均约定（新协议版本，预先登记）**：只有一个允许 token 的位置（强制 token）log-prob 为 0，梯度也为 0。PG 损失的分母改为"可分支 token 数"（允许集大于 1 的位置），这样不会被强制 token 稀释。KL 用同一个分母。
- **复用 661 adapter**：它没过原闸门，复用需要用户直接批准。新版本的 guard 要明确写上"原 76/80 闸门失败，24/80"，不能伪造原来的放行证明。

## 3. 测试和新闸门（CPU 上全部通过后才提交 GPU）
- A. 合法集测试：在 80/20 真实状态、4 个起点和随机合法状态上，trie 叶子和物理动作一一对应，没有反向重复，没有漏项。另外测：EOS 和 64 token 上限；死前缀或空合法集时直接失败（fail-closed）；tokenizer 编码解码往返一致；缓存不跨状态或版本复用。
- B. 概率一致性：在小词表上手算 trie 并穷举。要求采样时记下的 old log-prob、teacher-forcing 重算的 log-prob（更新前）、同权重参考模型的 log-prob 三者相等。另测 causal shift、padding/EOS 掩码、temperature 1、有无缓存等价、强制 token（log-prob 0、KL 0、梯度 0）、梯度有限、一次更新后参考模型不变。
- C. 诊断：记录干预率，并写明分母，把全部生成 token 和真正的分支 token 分开统计；同时记录被掩码去掉的未约束概率质量。661 的 24/80 留作基线。
- **GRPO 冒烟的新闸门**（替换原来的 19/20 合法率闸门）：采样到的动作 100% 能解析且合法（不合法说明有 bug，直接停）；GPU 上 old log-prob 和重算 log-prob 的差在预先登记的容差内；梯度有限；1 次更新加保存重载都成功；报告干预率和被掩码去掉的概率质量。
