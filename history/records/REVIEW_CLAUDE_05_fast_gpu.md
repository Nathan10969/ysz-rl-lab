# Claude 审核 05｜fast 协议精度，以及 GPU stub 驱动问题

日期：2026-10-23。依据：GPU_PILOT_RESULTS.md。BUDGET_REPLAN.md 只粗看了结构，没有逐项核对。

## 1. fast 协议：绝对能差 0.076 eV/胞，这个门槛当初定错了
- 我在审核 04 里定的"总能差 ≤0.02 eV/胞"，比较的是**绝对总能**。可我们的研究只用**同成分、同晶胞的相对能**，所以门槛应该定在相对能上。0.076 eV/316 原子 ≈ **0.24 meV/原子**，这是 LREAL=Auto 这类设置常见的系统性平移。力差最大 0.0065 eV/Å，RMSE 0.0018 eV/Å，都很小。现在还缺的是证据：这个平移在不同构型之间是不是基本不变。
- 还有一点：GPU 版 VASP 主要靠实空间投影加速，生产计算基本都会用 LREAL=Auto。所以 Auto 下的相对能是否可靠，**无论最后用 CPU 还是 GPU 都必须验证**。
- **门槛改为**：|ΔE_fast(L01−L00) − ΔE_ref(L01−L00)| ≤ 0.02 eV/胞，同时最大力差 ≤ 0.02 eV/Å。
- **放行一个参照作业**：09_L00_ref，在 CPU 上用旧协议（LREAL=.FALSE.，EDIFF=1E-6，vasp_std），只加上 AMIX=0.2、BMIX=0.0001 防止发散；128 核，墙钟上限 1.5 h，封顶 192 核时（按旧 L01 的成本估计实际约 60 核时）。ΔE_ref 就用它和旧 L01（−2997.39085 eV）来算。
- 仍然只有两个构型，这只能做一次健全性检查。后面 P1 的小胞会再补一组 Auto 和 .FALSE. 成对的对照（见第 4 点）。

## 2. GPU：nvhpc 模块把 CUDA 的 stub 驱动库放进了路径
诊断正确（错误码 34，CUDA_ERROR_STUB_LIBRARY）。这是**平台模块配置的 bug**：管理员给的 demo 脚本照样会失败。
- **放行修复后的重测**，但改成**串行**：先只跑 07r（1 张 A100，墙钟 59 分钟）。只有 07r 正常进入 SCF 并完成之后，才提交 08r（2 张卡）。累计封顶仍是 2.9511 卡时。
- 修复方式：作业里**从 LD_LIBRARY_PATH 中过滤掉含 `stubs` 的路径，以及 hpc_sdk 里的 `cuda/lib64`**，让系统使用计算节点上的真实驱动。只有过滤之后 cuInit 仍然失败，才改用 LD_PRELOAD 指定真实的 `libcuda.so.1`。预检失败就直接退出，不启动 VASP。这个做法可以接受。
- 请顺手**通知平台管理员**：nvhpc/25.3 模块路径中的 `cuda/lib64/libcuda.so(.1)` 是指向 stubs 的软链接，会让 GPU 程序初始化失败；另外，A100 文档里写的 IP 也是过期的。

## 3. 力的阈值
同意 Codex 的指正：力要单独用 eV/Å 来定阈值。GPU 与 CPU 一致性的门槛定为：总能差 ≤0.01 eV/胞，**最大力差 ≤0.02 eV/Å**。
